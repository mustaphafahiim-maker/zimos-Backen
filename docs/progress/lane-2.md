## Decisions
- 2026-10-03 Blocklist routes keep `customers.view` / `customers.manage` (as the existing blocklist did) instead of a new permission: existing roles in the database would not have a new one.
- 2026-10-03 `POST /fraud/blocklist` still accepts the old `{ phone, reason }` body; `GET` now returns `{ entries, nextCursor, counts }` of blocked entries. A blocked phone no longer creates a customer row; order creation reads `blocked_entries` directly and marks the customer on its first order.
- 2026-10-03 A `name_address` entry stores sha256(normalized name | normalized street line); the label keeps the readable text.
- 2026-10-03 CSV import takes the file's text in a JSON body (`{ csv }`, 1.5 MB max, 2000 rows): no multipart needed.
- 2026-10-03 An `orders` entry match adds the existing `blacklisted_customer` flag (and refuses when `block_blacklisted` is on); staff-created orders are not matched by IP.
- 2026-10-03 The machine allows 5 preview servers per folder and other lanes hold 4, so the lane API runs with `node src/server.js` in the background and features are verified through the API; the owner declined browser-pane use in this chat, so dashboard screens are typechecked, not clicked.
- 2026-10-03 Stored fraud rules are not rewritten by a migration: `resolveFraudRules` reads both the bare value and `{ value, action }`, and the dashboard saves the new shape.
- 2026-10-03 Strict phone validation uses per-country mobile patterns in `fraudRules.js` (no libphonenumber in the repo); the store country comes from `defaultLocale`. It answers INVALID_PHONE so the shopper can fix the number.
- 2026-10-03 `block_outside_country`, `block_vpn`, `min_network_delivery_rate`, `high_risk` are validated, stored and evaluated already, but only fire once items 3, 5 and 6 pass them the IP country, VPN flag, network rate and risk level. `require_otp` only flags until item 7; `to_lost` refuses like block until item 9 files the lost order.
- 2026-10-03 A blocked visitor gets the existing 423 STORE_UNAVAILABLE, so the storefront shows its unavailable page with no storefront change and nothing tells the visitor they were singled out. Decisions are cached 60s per store+IP.
- 2026-10-03 Blocked countries live in `settings.fraud_rules.blocked_countries` (one settings object for the whole protection screen). The shopper IP is X-Storefront-Client-IP when the storefront server proves itself with STOREFRONT_PROXY_SECRET, else req.ip.
- 2026-10-03 ipIntel: sandbox answers outside production only; in production with no IP_INTEL_PROVIDER every lookup is unknown, so country/VPN rules stay silent until the integrations team registers an adapter.
- 2026-10-03 Bot protection is on by default in production only; elsewhere it follows BOT_PROTECTION_DEFAULT (default off) so the other lanes' and the tests' direct checkout calls keep working. A store's own `fraud_rules.bot_protection` wins everywhere.
- 2026-10-03 A failed challenge-provider call (timeout, error) passes the shopper; only a definite "no" refuses. The storefront does not render a challenge widget yet: `captcha` in the guard answer is null until a real verifier is registered.
- 2026-10-03 Bot refusals carry `lostReason: integrity_check` on `req.checkoutRefusal`; item 9 turns them into lost orders.
- 2026-10-03 Risk is scored for storefront orders only (staff orders stay null). Device-based signals are skipped (no device id is collected); "more than two orders from the same IP in an hour" uses the IP. The AI gibberish check (P2, FeatureFlag) is not built.
- 2026-10-03 The orders list gets its risk filter as `?risk=` through my own component so lane 1's filter work on that page does not collide; low risk shows no badge in the list.
- 2026-10-03 Network stats are updated inside the stage change's own transaction (in a savepoint, errors logged, never failing the order) rather than by a worker: a few upserts, and no event is lost. `rejected` = the COD call rejected an order that was never confirmed; a cancel before confirmation counts nowhere.
- 2026-10-03 The pepper is NETWORK_STATS_PEPPER, falling back to a value derived from JWT_ACCESS_SECRET. The network score is not embedded in the order payload (lane 1 owns hydration); the list asks for a page of scores in one call.
- 2026-10-03 In the lane database the flag `customer_network_score` was switched on by hand for testing; everywhere else it is off until legal approves (SPEC §5.4).
- 2026-10-03 OTP settings live in `settings.fraud_rules.checkout_otp` (not `settings.checkout_otp`): the fraud_rules object already has the merge, validation and workspace.manage gate, and no shared settings file had to change.
- 2026-10-03 The OTP flow keeps no server-side pending order: the storefront re-submits the same checkout with a signed 30-minute proof for that phone and store. `awaiting_otp` / `otp_unverified` on the checkout session is item 9; the 428 already carries the refusal marker for it.
- 2026-10-03 A rule with action `require_otp` asks for a code even when the store's OTP switch is off; an online-payment order is not asked by rules (same exemption as block).
- 2026-10-03 Money saved = (refused checkouts + blocked-and-cancelled orders) × 2 × the store's average shipping fee over the last 90 days; a store with no paid shipping shows 0 with a note. "Prevented" counts audit rows `order.blocked`.
- 2026-10-03 The `status` enum of checkout_sessions is untouched: `lost`, `awaiting_otp` and `abandoned` are derived at read time from the new columns, like `abandoned` already was. Every refusal is filed; a plain `block` is filed as already reviewed, `to_lost` / OTP / bad data wait under review.
- 2026-10-03 `abandoned_after_minutes` lives in `settings.fraud_rules` with the other protection settings (default 15, was a constant 60). `checkout.abandoned` is only emitted for sessions that went quiet, were unverified or had bad data — never for blocked customers, bots, refused countries or limits, so no recovery message follows those.
- 2026-10-03 "Convert to order" places the order on the server from what the shopper typed, with a dialog to complete name, phone and address (lane 1's manual order screen was not there to pre-fill). Export is CSV with a BOM (opens in Excel), returned as JSON `{ csv, count, filename }`. `payment_failed` exists as a reason but nothing files it yet: unpaid online orders are real orders in `awaiting_payment`. Google Sheets sync for lost orders is lane 7's apps work.
- 2026-10-03 The device id is a random id in the browser's localStorage (not a fingerprint): clearing storage gives a new one. It travels in the checkout body and is kept on the request, not in the order payload.
- 2026-10-03 The AI order check calls the AI module's provider directly (no merchant-facing `ai_jobs` row and no count against the store's monthly AI limit: it is the platform's check, not a merchant request). A real provider must answer feature `order_check` with `{ is_gibberish, is_abusive, address_complete }`; the sandbox one does.
- 2026-10-03 The real Turnstile verifier (server side, secret key) is still the integrations team's; the storefront widget code for provider `turnstile` is written but could only be exercised with the sandbox provider here.

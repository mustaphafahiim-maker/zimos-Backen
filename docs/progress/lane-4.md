## Decisions
- 2026-10-03 Notifications are fanned out: one row per teammate (permission of the type + their preferences), so `readAt` is per person. `user_id` stays nullable as in the spec (a null row = whole team, shared read state).
- 2026-10-03 `/workspaces/:id/notifications` has no `requirePermission`: it is each member's own bell; the type's permission is applied at delivery. Marking read is not audited (noise); preference changes are.
- 2026-10-03 Channels built: `inApp` and `email` (existing provider). Web push / app / WhatsApp-to-merchant need providers that §14 puts out of scope.
- 2026-10-03 Title/body are stored in Arabic; `data` carries the values and the dashboard renders known types in the viewer's language.
- 2026-10-03 New-order sound is generated with Web Audio (no asset file); the header polls `/notifications/summary` every 20 s (SSE comes with item 7).
- 2026-10-03 Platform announcements are copied into a teammate's bell lazily when they list notifications (dedupe on announcement id).
- 2026-10-03 "Wallet running low" type skipped: there is no wallet (pricing is out of scope).
- 2026-10-03 Emitters wired: `order.created` (new order, suspicious when `riskFlags` is set, low stock of the ordered variants once a day). `integrationFailed()` and `exportReady()` exist in `merchantNotificationEvents.js` for other lanes to call; not yet called anywhere.
- 2026-10-03 The preview tool allows 5 dev servers per folder and 4 belong to other lanes, so the API is run with `node src/server.js` in the background and only the dashboard/storefront through `preview_start`.
- 2026-10-03 Pixels: GTM and Clarity are rows of the same table (platforms `gtm`, `clarity`, browser only); a Google Ads id (`AW-`) carries `config.adsConversionLabel` and has no server API. TikTok/Snap/GA4 have no test-code field because their existing providers do not send one.
- 2026-10-03 The legacy `settings.tracking_pixels` key and `/server-pixels` endpoints are left in place but nothing reads them any more; `GET /store/:ws` still returns the old `tracking` block (first store-wide pixel per platform) next to the new `trackingPixels`.
- 2026-10-03 Storefront scoping: all pixels are initialised, events go only to in-scope pixels (Meta `trackSingle`, TikTok `instance`, gtag `send_to`). A product-scoped pixel joins the visit once that product page was viewed (sessionStorage); funnel scope follows the analytics tracking context. Snap cannot target one pixel, so a scoped Snap pixel is initialised on first match and stays for the page session.
- 2026-10-03 `pages/marketing/MarketingPage.test.tsx` still describes the old one-ID-per-platform form and will fail; left untouched (no test work in lanes) — whoever revives the suite should rewrite or drop it.
- 2026-10-03 Server copies of browser events: only `view_content`, `add_to_cart`, `begin_checkout`, `add_payment_info`, `lead` are relayed (not `page_view` — one request per page per pixel, and the browser pixel already reports it). They carry no phone/email (anonymous); matching uses fbp/fbc, ttp/ttclid, Snap click id, IP and user agent, which the storefront now sends in the batch's `pixel` block. Purchase keeps `order.id` as its id.
- 2026-10-03 The relay uses lane 7's queue directly (`queue.add('pixels', …)`), not a domain event: a storefront event is not a business change. A platform that answers with an error is logged and not retried; only "unreachable" retries.
- 2026-10-03 "Send test event" sends a page view (never a conversion) so a merchant's ad account is not polluted; on Meta it uses the pixel's test event code when set.
- 2026-10-03 Providers: `call` is now exported from the four `pixelProviders/*` files; their Purchase code is untouched. Non-purchase bodies live in `pixelProviders/browserEvents.js`.
- 2026-10-03 `AddPaymentInfo` fires when the shopper picks a non-COD method in `PaymentMethodPicker`; `Lead` fires when an `opt_in` funnel step is continued (there is no opt-in capture endpoint yet — when lane 5/8 add a real form, call `track("Lead")` on its submit).
- 2026-10-03 `purchaseEventSentAt` (no second Purchase on refresh) is left to item 4, where Purchase timing is reworked; today the outbox consumer runs once per order and the browser side has `trackPurchaseOnce`.
- 2026-10-03 Delayed Purchase (`on_confirmed` / `on_delivered`) is sent when the order reaches that moment, stamped with that moment, through the unchanged provider `sendPurchase` — so it is always fresh and no platform's late-event window applies; the spec's "original event_time + action_source=system_generated" variant was not built because it needs changes inside the providers. An order created already confirmed counts for `on_confirmed` at creation. Existing orders were marked as already sent.
- 2026-10-03 Attribution rides on the analytics batch (`touches`) and is copied onto the order when its `purchase` event arrives, once, instead of going through the checkout request — the checkout contract (lanes 1/5) stays untouched. Orders with no purchase event (manual orders, blocked tracker) have no attribution. Falls back to the session attribution when the cookie is missing.
- 2026-10-03 A touch is recorded only for an arrival with a utm/click id/`ref`/outside referrer; a plain direct visit keeps the earlier touches. `sessionStats` = first visit, visits, page views, seconds on store, computed from `analytics_events` at purchase time.
- 2026-10-03 Lane 6's attribution report still reads UTM from the purchase event; `orders.attribution` is now there for it to switch to.
- 2026-10-03 Known gap kept from before: with `on_order`, an order that waits for an online payment is skipped at creation and nothing reports it when the payment later succeeds (no `order.paid` event exists yet).
- 2026-10-03 Automations: existing single-WhatsApp-action rules keep working unchanged (one step). An execution snapshots the rule's steps when it starts, so editing a rule does not change sequences already waiting; switching a rule off or deleting it stops them at their next step.
- 2026-10-03 Triggers beyond the seven order ones are accepted by the API and the consumer but only fire once their owners record the event in the outbox: `order.unreachable`, `order.postponed`, `order.returned`, `order.payment_failed`, `checkout.abandoned` / `lost_order.created` (payload `{ workspaceId, checkoutSessionId }`), `lead.created`, `subscription.renewal_failed`. `review.request` is `order.delivered` + a leading wait (`conditions.delayDays`, default 3).
- 2026-10-03 `set_status` supports `confirmed` and `cancelled` only and acts as the store owner (the confirmation queue and audit log need a real user). `{{coupon_code}}` is a per-rule value (`conditions.couponCode`). `{{recovery_link}}` uses the session's recovery token when lane 2 adds it, else the store's checkout URL.
- 2026-10-03 WhatsApp texts cannot be shipped by ZIMOS (Meta only sends templates approved in the merchant's own account): each ready-made automation names its template(s) and shows the Arabic body + buttons to submit to Meta. Until approved, that step fails with Meta's error in the run log.
- 2026-10-03 The rule editor has no picker for `productIds` / `funnelIds` conditions yet (the API accepts them and the editor preserves them). `AutomationsPage.test.tsx` describes the old single-action editor and will fail if the suite is revived.
- 2026-10-03 New notification type `automation` (the `notify_team` step), delivered to teammates who may see orders.
- 2026-10-03 Quick replies: always on (no setting) — a store that does not want it simply does not put buttons on its template. Typed text counts only when it is exactly a confirm/cancel word *and* quotes one of our order messages; anything else stays an inbox message. When the order cannot be changed automatically (an agent holds the task, already shipped, courier must be told) the team gets a bell notification instead. The change is recorded as done by the store owner with a note saying the customer tapped the button.
- 2026-10-03 The order behind a reply is found through the quoted message (`context.id` → `whatsapp_messages.order_id`); only automation sends set `order_id` today — the inbox's manual sends can pass `orderId` to `sendMessage` when item 7 adds order actions.
- 2026-10-03 Inbox live updates: SSE, not WebSocket. Events only say that a conversation changed; the page re-reads through the normal API (its existing 10 s polling stays as the fallback). In-process publish for instant delivery plus a 5 s `MAX(updated_at)` poll per connection, so it also works with a separate worker and no Redis. The stream lives at `/api/v1/inbox-stream/:workspaceId` because everything under `/workspaces` demands a staff session and EventSource cannot send a header; it takes a one-minute HMAC ticket from `POST /inbox/stream-ticket` and re-checks membership + `orders.confirm`.
- 2026-10-03 Inbox permissions follow the existing WhatsApp routes (`orders.confirm`); assignees are the teammates holding it. Assignment is a label and a filter — it does not stop another teammate from replying.
- 2026-10-03 Customer panel actions use the existing order endpoints (confirm with channel `whatsapp`, cancel). "Create order" links to the orders list until lane 1's manual-order screen exists. Delivery rate here is the store's own (delivered ÷ finished orders); lane 2's cross-store network score is separate.
- 2026-10-03 The mock's `open|bot|resolved` statuses are not used: the page already ran on the real `open|closed`.
- 2026-10-03 Order emails start switched off for every store (nothing emails a store's customers until its merchant turns it on). `order_refunded`, `abandoned_cart` and `digital_delivery` listen for `order.refunded`, `checkout.abandoned` and `digital.delivered`, which nobody records in the outbox yet — they send once those events exist. Body is plain text with variables (escaped, URLs made clickable), wrapped in the store's logo/colour; no HTML editor.
- 2026-10-03 Sender: the platform's sending address with the store's name as sender name (`brevoEmailProvider.sendEmail` gained an optional `fromName`). The merchant's own sending domain (SPF/DKIM screen, "Verify") is out of scope per §14's boundary and not built.
